# olmo3-embed: plan

**Goal:** turn **OLMo 3 7B** (Ai2, Apache-2.0, released Nov 2025) into a dense text-embedding model that is
competitive on the **MTEB BEIR benchmark** (15 retrieval tasks, nDCG@10 average). Training is split between
**Google Colab** (A100/H100, the heavy runs) and a **local RTX 5070 Ti Laptop GPU (12 GB)** (dev loop, data work,
small-model ablations, fast eval).

**Our angle:** the first *fully open* 7B embedder: open base model, open pretraining data (Dolma 3), and open
fine-tuning data and code. Because the pretraining data is public we can **audit BEIR contamination** ourselves,
which closed-data models (Qwen, Mistral, Llama based) can't offer. It also helps on the leaderboard, which shows a
zero-shot score next to each model.

## 2. Hardware split

| | Local RTX 5070 Ti Laptop (12 GB) | Colab (A100 40/80 GB, H100 80 GB) |
|---|---|---|
| Role | Dev loop, data pipeline, ablations, NanoBEIR eval | Full 7B training, full BEIR eval |
| OLMo-3-7B | Too big for bf16 (~14.6 GB). Only QLoRA 4-bit with short seqs; use it for smoke tests, not real runs | bf16 + LoRA + GradCache |
| Proxy model | **OLMo-2-0425-1B** in bf16 (same family and tokenizer lineage, fits easily) for recipe ablations | – |
| Hard-negative mining | Embed corpora with a small teacher (e.g. Qwen3-Embedding-0.6B / bge-base) and search with FAISS | Big-teacher mining if needed |
| Eval | **NanoBEIR** (13 tasks × ~5k docs, minutes) as the inner-loop metric | Full 15-task BEIR (~30M+ docs encoded; plan ~6–12 GPU-h per 7B eval) |

**Colab survival rules.** Sessions die. Every run must:
1. Checkpoint the LoRA adapter, optimizer, data cursor and RNG to Google Drive or a private HF Hub repo every N steps.
2. Resume idempotently with `--resume auto`.
3. Cache encoded BEIR corpora per (model, checkpoint) shard so an interrupted eval resumes instead of restarting.
4. Log to W&B (or a JSONL file synced to Drive).

Code lives in this repo. Notebooks are thin launchers: `git clone`, `uv sync`, `python -m olmo3_embed.train --config ...`.
No logic lives in notebooks.

## 3. Model recipe

The base is `allenai/Olmo-3-1025-7B` (base, **not** Instruct/Think; check the exact HF id). Ablate base vs Instruct
once.

| Decision | Default | Ablation |
|---|---|---|
| Attention | **Bidirectional** (remove causal mask, as in LLM2Vec and NV-Embed) | Causal (as in Qwen3-Embedding) |
| Pooling | **Mean pooling** if bidirectional; **last token (EOS)** if causal | Latent-attention pooling (NV-Embed) |
| Adaptation step | MNTP (masked next-token prediction) warm-up of ~1k steps if bidirectional (LLM2Vec showed it matters) | Skip MNTP |
| Fine-tuning | LoRA r=16–32 on all linear layers, bf16 | Full fine-tune (only if budget allows) |
| Loss | InfoNCE, τ≈0.02, in-batch negatives + 7 mined hard negatives, GradCache to reach effective batch 512–2048 | + KL distillation from cross-encoder scores |
| Instructions | Task-specific query instruction (`Instruct: {task}\nQuery: {q}`), documents get no instruction | Generic instruction |
| Output | 4096-d, **Matryoshka** loss at 256/512/1024/4096 | – |
| Depth | Full 32 layers | **Truncated to 16–24 layers** (mid-layer embeddings are often as good; halves cost and fits a 12 GB laptop in bf16) |
| Final step | Merge 2–4 checkpoints or data-mix runs (model soup / slerp) | – |

## 4. Data

**Two tracks.** Report both and decide which to submit:

- **Track A: zero-shot-clean.** Training data excludes every BEIR task's train split (MS MARCO, NQ, HotpotQA,
  FEVER, FiQA, Quora, SciFact, and so on). Sources: synthetic data (below), S2ORC/Wiki pairs, StackExchange, PAQ,
  and other non-BEIR sets. Yields the honest zero-shot number and the open-data story.
- **Track B: standard-practice.** Adds the BEIR train splits that E5-Mistral, NV-Embed, bge-en-icl and Qwen3 all use
  (MS MARCO, NQ, HotpotQA, FEVER, FiQA, Quora dupes, and so on). This is what's needed to reach T2/T3.

**Pipeline (`src/olmo3_embed/data/`):**
1. **Ingest** public pairs (sentence-transformers `embedding-training-data`, `bge-full-data`, E5 public mix) into a
   unified `(query, pos, negs[], task, instruction)` parquet schema.
2. **Dedup and decontaminate.** Exact and MinHash removal of anything overlapping BEIR test queries or qrels docs.
   Same check against Dolma 3 for the contamination report.
3. **Hard-negative mining (local GPU).** Teacher retrieves the top 100. Keep negatives from ranks 30–100. Apply
   **positive-aware false-negative filtering**: drop a negative if its score is above 0.95 × the positive's score
   (NV-Retriever).
4. **Synthetic data from subscription CLIs, with several generators.** *Decided 2026-10-04: use Pete's existing
   subscriptions for personal open research.* To keep output short, use **passage → query** generation rather than
   writing passages from scratch:
   - Sample real passages from open corpora that aren't BEIR test corpora (Wikipedia, S2ORC abstracts,
     StackExchange, and so on).
   - Pack ~20 passages per call. The model writes a BEIR-shaped query for each (argument, claim, financial question,
     duplicate question, entity search, and so on), plus a task instruction, returned as JSON.
   - Hard negatives come from local mining (step 3), not from the LLM.

   **Generator backends** live in `src/olmo3_embed/data/synth/`, with one adapter per CLI and a shared prompt and
   JSON schema:

   | Backend | Plan | Headless call | Limit to plan around |
   |---|---|---|---|
   | **Claude Opus 5.5** (primary) | Claude Max | `claude -p --output-format json` | Max session and weekly usage windows |
   | **OpenAI Codex** | ChatGPT Plus ($20) | `codex exec` | 5-hour usage window on Plus (reinstated 2026-08-25) |
   | **Gemini via Antigravity** | Google AI Pro | `agy -p` / `agy --print` | Gemini CLI no longer serves AI Pro (since 2026-06-18). `agy -p` has a known hang on Windows non-TTY, so run it from WSL/Linux |
   | *(fallback)* any Batch API | pay per token | SDK | ≈ $10–20 per 50k examples (Haiku 4.5 / Sonnet 5.5 batch) |
   | **Olmo-3.1-32B-Instruct** (fully open; decided 2026-10-05) | Colab credits | vLLM on H100/A100 80GB | No usage window; also the bulk relevance judge in Phase 3 (`docs/phase3-plan.md` §4b) |

   Why use several: mixing generators increases query diversity, which helps synthetic retrieval data. Every row
   records `generator` and `model` so we can ablate a source, or drop it later if its terms or quality become an
   issue. Throughput: 50k examples ≈ 2.5k calls of 20 passages, so spreading the calls across three subscriptions
   over a few days fits comfortably inside the usage windows.

   Plan: a 2k-example pilot on each backend, then pick the mix by downstream NanoBEIR score (not by eyeballing),
   then scale to 50k–200k.
5. **Mixing.** Batches are homogeneous per task (in-batch negatives from the same task). Sample tasks with a
   temperature over dataset sizes.

## 5. Compute budget (rough, to sanity-check)

Assume 7B with LoRA, ~150 tokens on average per text, and 1 query + 1 positive + 7 negatives per example ≈ 1.35k
tokens per example. Then:

- 300k examples × 1 epoch ≈ 0.4B tokens → 6 × 7B × 0.4B ≈ **1.7e19 FLOPs** (GradCache's extra forward roughly offsets LoRA's cheaper backward), about **15–30 H100-hours** or
  **40–80 A100-hours** at realistic MFU.
- Each full BEIR eval: 6–12 GPU-hours.
- MNTP warm-up: a few GPU-hours.

**Colab Pro in compute units (CU).** Pro is $9.99/month for 100 CU; top-ups are $9.99 per 100 CU. Community-measured
burn rates from March 2026 (Google doesn't publish them, so check the Resources panel):

| GPU | CU/hr | ≈ $/hr | Use for |
|---|---:|---:|---|
| L4 22.5 GB | ~1.7 | $0.17 | **Full BEIR eval** (7B bf16 inference fits; best FLOPs per CU) |
| A100 40 GB | ~5.4 | $0.54 | **7B training** (bf16 + LoRA + GradCache fits) |
| A100 80 GB | ~7.5 | $0.75 | Only if 40 GB OOMs at the target batch or sequence length |
| H100 | unpublished | – | Measure before committing |

**First 7B run cost:** 40–80 A100-40GB hours ≈ 220–430 CU ≈ **$22–43**, plus a full L4 eval of ~10 h ≈ 17 CU ≈ **$2**.
That matches the "<$50 for the initial run" quote. Pro's 100 CU covers about a quarter of it; the rest is 2–4 top-ups.
This assumes the ~300k-example scale above. A 100k-example first run costs about a third as much.

**Pro caveats:** no background execution, so the browser tab must stay open during runs, and premium GPUs are
subject to availability. The §2 checkpoint and resume rules are mandatory, not optional.

**Background execution options:**
- **Colab Pro+** ($49.99/month, ~500–600 CU; check the signup page) adds background execution, which keeps the
  runtime alive after the tab closes, plus higher GPU priority. Its monthly units roughly cover one full 7B run, so
  **upgrade to Pro+ for the month of Phase 4** and stay on Pro otherwise.
- **Colab Enterprise** (Google Cloud): fully headless notebook executions and schedules
  (`gcloud colab executions/schedules`), billed per VM-hour at GCP rates. That's noticeably more per A100-hour than
  consumer CUs, so use it only if we want CI-style unattended runs.

**Implication:** budget roughly 3 full 7B training runs plus ~6 full evals for the whole project, and run *every*
ablation on the 1B proxy locally with NanoBEIR first. Truncating depth (§3) is the biggest single cost lever.

## 9. Risks

- **Score ceiling:** Qwen3-Embedding had 150M synthetic pairs plus multi-stage training. T3 needs good synthetic
  data, not just tuning.
- **OLMo 3 quirks:** check tokenizer EOS handling for last-token pooling, the sliding-window attention layers
  (if any) when removing the causal mask, and `flash-attn` support on sm_120 locally (fall back to SDPA).
- **Eval drift:** MTEB v2 changed some task versions and splits. Always pin the `mteb` version and record it with
  results.
- **Colab preemption:** mitigated by §2 survival rules. Never run a job longer than ~6 h without a checkpoint.
